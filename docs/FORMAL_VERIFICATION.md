# Formal verification (Lean 4)

`AGENTS.md` asks for Lean 4 verification of algorithmic correctness. The Lean project lives in `formal/` (toolchain pinned in `formal/lean-toolchain`, no Mathlib, no `sorry`, no axioms).

## What is not proved

- The correspondence is tested on finite grids, not proved for all inputs. The grids are exhaustive over the discrete structure (every state, every branch of every condition) but not over unbounded numbers or arbitrary strings.
- Floating-point behaviour (NaN handling in budgets, CAGR, PER, margins) is covered by unit and property tests, not Lean: the models use natural numbers.
- Time is abstracted to one bit (`leaseExpired`); clock skew is outside the model. Fencing does not depend on clocks, which is the point of the generation counter.
- The reducer model abstracts component props and reference checks (datasets, sources); those are covered by unit, property and integration tests.
- SQL-level atomicity (the guarded D1 batches) is exercised by integration tests in the Workers runtime, not modelled.
- Feed parsing, URL/IP classification and claim text matching are not modelled.
- String truncation (`truncateText`, now in `packages/domain/src/text/truncate.ts`) and the context builder's text handling in `buildConversationContext` (trimming, the per-message cut, UTF-8 byte counting) are covered by unit and property tests, not by Lean; only the selection count (`recentCountWithinBudget`) is modelled.
- The dashboard model abstracts widget props and the 30-series limit (titles, sizes, series sets); those are covered by unit, property and contract tests. `replace` (same widget id) is structurally the identity and `reset` installs a schema-validated dashboard, so neither needs its own operation in the model.
- The rate-window model counts whole time units; sub-millisecond timing and the runner's sleep/pacing are outside the model. The bound assumes grants are recorded in clock order, which holds because the runner appends them as they occur.
- The calendar fold model abstracts characters to their UTF-8 widths (1..4 octets): the implementation never looks at the characters themselves, only at each one's width, and the conformance test replays every vector through real one- to four-octet characters. The selection model abstracts validated ISO dates to day offsets from a fixed base (lexicographic string order is chronological order on validated `YYYY-MM-DD`); invalid date strings, negative or fractional counts and undecided dates are outside the Nat model and are covered by unit tests plus a fail-closed conformance section.
- The month-grid model proves the combinatorial core (offsets in `Nat`); the absolute civil-date correspondence (leap years, the 1970 Thursday anchor, Hinnant arithmetic) is an independent Lean reimplementation used only for the 27 exported vectors, tied to the TypeScript by the conformance test and by hand-worked unit tests — tested on samples, not proved. `shiftMonth` and `groupEventsByDate` are covered by unit tests, not modelled.
- The sync-plan model abstracts all compared fields to one fingerprint per event (equal iff every compared field is equal) and ids to small `Nat`s; transparency is a separate `busy` flag on managed rows, because every desired body is `transparent` and so has no busy variant to fingerprint; duplicate ids in either input are outside the model (the implementation fails closed with `DUPLICATE_ID`) and are covered by unit tests plus a fail-closed conformance section. The exact ascending output order is pinned by the vectors and asserted in the conformance test; only membership is proved about the model's sorts. The base32hex encoder has vectors plus a proved output-length property; the digest canonical form (`canonicalGoogleSyncDigestInput`) is covered by unit tests and the bench case, not modelled.
 - The drop-target model uses integers for coordinates while the implementation uses doubles; every conformance vector is integral so the two agree exactly, and the doubled-center dot product has the same sign as the midpoint version. Slot measurement from the DOM, the `requestAnimationFrame` coalescing and the page-coordinate conversion in the drag engine are outside the model and covered by E2E; a negative `draggedIndex` is outside the `Nat` model (the implementation holds still for it, as for any out-of-range index). `banned_only_while_inside` assumes the engine invariant `previous.target = draggedIndex`, which is what the engine passes; histories with a different target are covered by vectors but not by that theorem.
 - The chart-window model uses integer days and natural-number values (prices; volumes are integers so a negative one can be stated and refused). Non-finite bar numbers, which `usableBar` also refuses, have no integer counterpart and are covered by unit tests. Floating-point behaviour (moving-average values, `windowStats` averages, percents and drawdown, `rebasePercent`, `autoInterval` estimates) is covered by unit and property tests, not Lean: only the moving-average null prefix and length are modelled. The calendar correspondence (civil-date mapping, the Monday bucket rule, month-end clamping in presets) is an independent Lean reimplementation used only for the exported vectors, tied to the TypeScript by the conformance test (which replays every vector through real `YYYY-MM-DD` dates and asserts each returned `bar.day` directly) and by hand-worked unit tests — tested on samples, not proved. Bucket-key monotonicity (sorted days give sorted keys) is likewise tested, not proved: the ascending theorems take it as a hypothesis. `inNextBucket` (the chart readout's "the bar one period before", ADR-0069 §7) compares two bucket keys and is likewise covered by hand-worked unit tests, not Lean. Daily output is nondecreasing (duplicate input dates intentionally yield duplicate bar days); only bucketed intervals ascend strictly. The TypeScript window functions reject non-finite day coordinates (`NON_FINITE_DAY`) before reaching the integer model, and the zoom anchor guarantee is qualified to valid positive factors (an invalid factor clamps). The zoom vectors skip the float-ambiguous anchor shifts (exact-division cases where the float floor could misround, covered by unit tests instead); every other combination is replayed exactly.
 - The trading-axis model computes over exact rationals; the TypeScript computes in floating point, so the conformance test compares within 1e−9 relative and the property test (`packages/domain/test/market/tradingAxis.test.ts`) checks the float round trips within tolerance, bar days on their index exactly, strict increase on quarter days and continuity at bar days. The model's `axisSegment` is a linear prefix scan, the TypeScript's a binary search: equal on ascending lists, pinned by the vectors' `segment`, not proved. Lists that are not strictly ascending (duplicates, out of order) are outside the theorems: both sides fall back to `day − first` / `first + position` on a segment without a positive gap and stay total, but the vectors do not cover them; the viewer's `unionBarDays` produces ascending distinct days. Non-finite inputs give NaN in the TypeScript and have no rational counterpart (unit tests).
- The stock-search model starts after NFKC: Unicode normalization is outside it. Text is a list of code points; whitespace is the set `/\s/u` matches that NFKC leaves unchanged (TAB, LF, VT, FF, CR, SPACE, U+1680, U+2028, U+2029, U+FEFF — every other `\s` code point normalizes to SPACE), so on NFKC-normalized text the model's whitespace test is exact. The TypeScript slices the query and compares symbols and markets by UTF-16 unit, the model by code point; they agree on the Basic Multilingual Plane, and the conformance test checks that every vector string is NFKC-stable and BMP. `fold_idem` holds for the model on NFKC-stable text. The TypeScript adds one step outside the model: a hiragana わ/ゐ/ゑ/を followed by U+3099 has no precomposed hiragana form, and only composes (to ヷ, U+30F7, etc.) after the shift to katakana, so the fold composes its output again (NFC) whenever it holds a kana voicing mark (found by this model's idempotence check; covered by `packages/domain/test/watchlist/stockSearch.test.ts`). The numeric `limit` is modelled as an integer; `NaN` and fractional limits (`Math.trunc`) are outside the model. The SQL ranking in the API is tied to this TypeScript reference by its own Workers-runtime test, not by Lean.

 - The schedule model works in natural-number local minutes from 1970-01-01 (the vectors stay at or after 1970; the TypeScript also accepts earlier dates, covered by unit tests). Its calendar sums month lengths instead of using Hinnant's closed form; the conformance test checks `localMinuteOf` against the model's minute for every sample instant, so the two calendars agree on samples, not by proof. **Time-zone resolution is outside the model**: `timeZone.ts` (`Intl` offsets, `utcMsToLocalMinute`, `localMinuteToUtcMs` with Temporal's `compatible` disambiguation, and `nextRunAtMs`'s walk over resolved slots) is covered by unit and property tests over Asia/Tokyo, UTC, America/New_York (spring-forward gap and fall-back overlap) and Europe/London (`packages/domain/test/schedule/timeZone.test.ts`). The parsing of `HH:MM` and `YYYY-MM-DD` text, fractional input minutes and the schedule contract's zod bounds are covered by unit tests. The tick model takes the schedule function as a parameter; that the shell passes `nextRunAtMs` bound to the task's own schedule and zone, and stores the fire's result with compare-and-set, is covered by the application and integration tests.

 - The page-series model abstracts series and list ids to natural numbers and widgets to two inputs (the named series in widget order and the list widgets' list ids in widget order), so which widget types name series, and where the list widgets stand among the others, are outside it; the conformance test replays every vector with every series-naming widget type and three widget orders. The stock → price series mapping (`stockPriceSeriesId`, the JPX suffix) is not modelled: its round trip through `parseStockId` and `parseMarketSeriesId` for every stock id shape, and that two stocks never share a series, are property tests (`packages/domain/test/watchlist/lists.test.ts`). That the API and the web resolve lists from the same storage the same way (`/watchlist` against the repository), and the 60-series runner claim and the uncapped clean-up keep set built on top of the page, are covered by the application and integration tests.

 - The history-refresh model uses day numbers for the `YYYY-MM-DD` dates (the code orders them as text, which is the same order) and integers for values (the code only compares values for equality, so any exact number behaves alike; the code's `===` also takes `0` and `-0` as one number, as SQLite does). `confirmed` states what the binary search computes on an ascending date-unique answer; the binary search itself is replayed by the 270 `historyConfirmed` vectors, not proved. That the answers really are ascending and date-unique is the adapters' guarantee, covered by their unit tests (`packages/adapters/test/finance/*Series.test.ts`); a non-finite `historyCheckedAtMs` is `none` in the model and covered by a unit test. The SQL that applies a write (delete, upsert-if-changed, trim, stamp) is tested against `mergeHistory`, not modelled.

 - The financial-statements model uses day numbers for ISO dates, order-preserving numbers for filing ids and integers for decimal values (the selection only compares, negates and sign-tests values; canonical decimal text is equal exactly when the numbers are); the conformance test replays every selection with integer and with fractional text. Date and decimal parsing (invalid ISO strings, which the code ignores or rejects) and `isCanonicalDecimal` are covered by unit tests, not Lean. `selectFiscalYearMetrics`, `deriveFreeCashFlow`, `annualFactsOfFiling`, `filingStaysPending` and the extraction are covered by unit tests. `select_congr` needs coherent filings; with one filing id under two standards the code's choice can depend on fact order (the database prevents it by storing date and standard once per filing). `reportedValueCount` is the revision history: an older filing with a different value raises it, which is why `select_older_irrelevant` compares results without it; the sync recomputes every metric-year its new facts touch, so it stays exact. The model keeps a mapping's sign (`negate`) and every theorem covers it, but no row of the real table negates today (SEC and J-Quants both report payments in the metric's convention), so the vectors replay only sign `1` (a negating row of a vector metric would fail the mapping-row comparison until the Lean table has it too). The J-Quants extraction (which `FYFinancialStatements_` records become filings, the `NC…` items as scope `separate`, the earnings-report / amendment order, ADR-0059 §2) is covered by the runners' unit tests, not Lean.

 - The sync-days model starts at day numbers: parsing `YYYY-MM-DD` (`isoDayNumber`; an invalid window end plans nothing, an invalid known day is ignored) and the conversion back are covered by unit tests (`packages/domain/test/sync/syncDays.test.ts`), and the conformance test converts the model's days through `Date`, independently of the code, so the weekday arithmetic agrees with the real calendar on every vector. The code keeps the blocked days in a `Set` and the model scans the known list (`any`): equal by construction, pinned by the duplicate-entry vectors, not proved. The cap is an integer in the model; the code floors a fractional cap, which no caller passes (outside the model, not tested). Which window and cap a job passes (the market-local date, the provider's history limit, the per-job day count) is the callers' and is covered by their tests.

 - The stock-mention model starts at the term characters: how a term is built from stored names (`nameMentionTerm`: NFKC, whitespace runs to one space, corporate forms and SEC state tags removed, the length bounds; `stockMentionTerms`: distinct names case-insensitively, then a US symbol, at most four) is outside it, as the stock-search model leaves NFKC out, and is covered by `packages/domain/test/news/stockMentions.test.ts`. Text is a list of UTF-16 code units, as the TypeScript indexes it (`charAt`, `length`); `mentionLikePattern` walks code points (`for … of`) and so does the model, grouping a high surrogate followed by a low one into one piece and every other unit into its own, which is what `for … of` yields. The byte count is UTF-8 over those pieces (a pair 4 bytes; a lone surrogate 3, as both the TypeScript's `codePointAt` arithmetic and `TextEncoder`, which writes U+FFFD, count it); the conformance test checks each pattern's count against `TextEncoder`. That D1's limit is 50 bytes of the pattern text is the reviewer's finding (D1 answers "LIKE or GLOB pattern too complex"), not modelled; the API tests run the real query. SQLite reads characters as code points: on well-formed UTF-16 (stored text and terms are; the conformance test checks every vector string) its `%` and literals agree with the model's, since a literal surrogate pair from a well-formed term can only match at a code-point boundary. Its `_` does not — on an astral character it takes the whole surrogate pair, the model one unit — so the prefilter theorem rests on an assumption the pattern meets by construction: `_` stands only for a separator, which matches only SPACE or `-`, one unit and one code point. The `like` vectors leave the astral-text × `_` pairs out for that reason, and the conformance test replays the rest, and every true occurrence's pattern, on real SQLite. The model of `LIKE` assumes SQLite's defaults (ASCII-only case folding, `case_sensitive_like` off), which D1 keeps. Which batches the API scans, the cursor and the page limits are covered by the API tests on real D1 and SQLite, not modelled.

 - The business-section model takes the marks and sizes as given: how a converted 10-K's blocks are marked (the "Item 1. Business" and "Item 1A / 1B / 1C / 2 / 3" heading patterns and their length bounds) and measured, the SEC cleaning of the body, and the rules of `businessParagraphs` (whitespace collapse, list markers, the heading test, the 20,000-unit / 400-paragraph budget with the first paragraph cut) and `businessSummaryCount` are covered by unit and property tests (`packages/domain/test/finance/businessDescription.test.ts`, the adapters' tests) and replayed by the Rust runner from TypeScript-generated vectors, not modelled. Sizes are natural numbers in the model; the TypeScript counts a missing, negative, fractional or unsafe size as 0, which the unit tests cover. The Rust port (`crates/research-domain/src/finance/business_description.rs`) also replays this family.

 - The period-change model fixes which two observations are compared; the subtraction and the percent (floating point, a zero base giving a null percent, non-finite values giving `NON_FINITE`) and ISO parsing are covered by unit tests (`packages/domain/test/market/changes.test.ts`). The code compares the mark with ISO dates as text, the model with day numbers: the same order for valid dates.
