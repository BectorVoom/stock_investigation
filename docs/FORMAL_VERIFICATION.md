# Formal verification (Lean 4)

`AGENTS.md` asks for Lean 4 verification of algorithmic correctness. The Lean project lives in `formal/` (toolchain pinned in `formal/lean-toolchain`, no Mathlib, no `sorry`, no axioms).

## What is proved

| Lean file | Mirrors | Theorems (plain language) |
|---|---|---|
| `JobStateMachine.lean` | `packages/domain/src/jobs/stateMachine.ts` | Terminal states are exactly the states with no successor and are absorbing; no path ever leaves a finished job (`terminal_is_final`); every state can reach a terminal one; every leased state can return to `pending`, be cancelled and be failed; `completed` is reachable only from `publishing`, `publishing` only from `verifying`, a lease only from `pending`; `partial` needs collection to have started; a pause for approval is possible only from a stage that can spend and resumes only through the queue; no self-transitions. |
| `Lease.lean` | `packages/domain/src/jobs/lease.ts` | A granted claim increments attempt and generation by exactly one and never exceeds the retry ceiling; cancelled, finished and live-leased jobs are never claimable (single lease); after a re-claim every proof with an older generation is rejected whoever presents it (fencing) and never becomes valid again; at most one (runner, generation) pair passes the lease check (mutual exclusion); the claimant's own proof is accepted. |
| `Budget.lean` | `packages/domain/src/jobs/budget.ts` | The budget check is sound and complete; usage is monotone; a run that performs each step only after the check passes never exceeds any ceiling, for any sequence of requested steps; with a zero spend ceiling no positively-priced step is allowed. |
| `Workspace.lean` | `packages/domain/src/workspace/reducer.ts` (structural part) | An accepted command was written against the current version and bumps it by exactly one; a stale command is rejected; the same expected version can never be accepted twice (idempotent submission); every accepted operation preserves "component ids unique and the layout lists each exactly once" — including a pigeonhole proof that the reducer's one-directional layout check is sufficient; applying any list of instructions with rejects skipped keeps the invariant and moves the version by at most one per instruction. |
| `Dashboard.lean` | `packages/domain/src/market/dashboard.ts` (id structure), `packages/widget-grid/src/core/layout.ts` | Every accepted edit preserves id uniqueness; `move` and `reorder` yield a permutation of the same ids (same length, same members); `reorder` lands at the requested index (`reorder_lands`) and keeps the relative order of the rest (`reorder_keeps_order`); `remove` removes exactly that id and keeps the relative order of the rest; `add` appends and never exceeds the maximum; a rejected `reorder` is `none` exactly for an unknown id or an out-of-range target (`reorderIds_none_iff`); rejected edits contribute nothing to an edit sequence. |
| `DragTarget.lean` | `packages/widget-grid/src/core/dragModel.ts` | The returned target is the previous target or a slot containing the pointer (`target_previous_or_hover`) and always splices in range (`target_in_range`); outside every slot the target holds (`hold_outside_slots`); the banned slot cannot be re-entered while the pointer stays inside it (`hold_over_banned`); a changed target always bans the vacated index (`commit_bans_vacated`) and needs a past-the-midpoint crossing in the travel direction, or coincident centers (`commit_needs_crossing`); under the engine invariant a held target keeps the ban only while the pointer stays inside it (`banned_only_while_inside`). |
| `RateWindow.lean` | `packages/domain/src/market/rateWindow.ts` | If a grant is recorded only when `permit` allows it, no window ever contains more than `maxPerWindow` grants (for grant times in clock order). |
| `Classification.lean` | `finance/filings.ts`, `evidence/verifyClaims.ts`, pipeline verifier rule | Exact characterisation of each reported-position change; a "supported" claim always has verified support, no contradiction and no unsupported number; contradictions surface as "conflicting"; the independent verifier can only downgrade, never upgrade. |
| `RecentWithinBudget.lean` | `text/recentWithinBudget.ts` | The kept count never exceeds `maxItems` or the number of items; the kept total never exceeds `budget`; when the count is smaller than both, adding the next older item would exceed `budget` (maximality, so no item is ever skipped). |
| `Calendar.lean` | `calendar/ics.ts` (`foldIcsLine`), `calendar/upcoming.ts` (`selectUpcomingEarnings`) | Every folded line is within the 75-octet limit, and flattening the folded pieces gives back the input list; the selection has at most `maxItems` entries, every entry lies in the window, and the result is sorted by (date, stock id). |
| `MonthGrid.lean` | `calendar/monthGrid.ts` (`buildMonthGrid`) | The cell count is a multiple of 7 (4–6 whole-week rows for real months); the first cell's weekday is `weekStart`; the in-month cells are exactly days 1..n in order. |
| `GoogleSync.lean` | `calendar/googleSync.ts` (`planGoogleSync`) | Every desired id ends in exactly one of inserts/updates/unchanged (under distinct ids, which the implementation rejects with `DUPLICATE_ID`); no id is both written and deleted; applying the plan to `existing` yields exactly the desired confirmed set (plus untouched cancelled leftovers). The base32hex encoder is modelled for vectors only (output length is proved: one 5-bit group per five input bits). |

## How the proofs are tied to the TypeScript

A Lean proof is about a Lean definition, not about TypeScript. The link is differential:

1. `formal/Export.lean` evaluates the **verified** definitions over exhaustive small grids and prints `formal/vectors.json` (state lists and the full transition matrix; 768 `decideClaim` cases; 288 `checkLease` cases; 768 budget cases under one fixed small budget; all 1,110 operation sequences of length ≤ 3 over a ten-operation alphabet for the reducer; 80 version-guard cases — every operation against three setups, each submitted with a stale (where one exists), the current and a future expected version, then resubmitted unchanged; 612 dashboard cases — every id list of length 0..3 over ids {0, 1, 2} without duplicates plus one full 24-widget dashboard, each against all 36 edits (16 add/remove/move plus 20 reorder over ids 0..3 and toIndex 0..4); 1,092 `ratePermit` cases — every grant list of length 0..2 over {0, 1, 5} against 7 timestamps, 3 ceilings and 4 windows; 120 recorded-grant traces over non-decreasing time lists; classifier grids; 2,040 `recentWithinBudget` cases — every list of length 0..3 over sizes {0, 1, 2, 3}, every budget 0..5, every `maxItems` 0..3; 111 `foldWidths` cases — every width list of length 0..3 over {1, 2, 3, 4} octets plus width runs around the 75-octet first line and the 74-octet continuation lines; 1,032 `selectUpcoming` cases — every row list of length 0..2 over a six-row alphabet (one undecided row, five dated rows over three stocks and three day offsets), every `today` in {0, 1}, every `daysAhead` in {0, 1, 3}, every `maxItems` in {0, 1, 2, 5}; 27 `monthGrid` cases — nine sample months (epoch edges, leap and common Februaries, 4/5/6-week grids) against week starts {0, 1, 6}, each with first weekday, day count, leading offset, row count, first cell date and the full in-month date list; 638 `syncPlan` cases — every desired pair list of length 0..2 over a five-pair alphabet and every managed-row list of length 0..2 over a six-row alphabet, both filtered to distinct ids; 17 `base32hex` cases — the empty input, twelve 5-byte boundary inputs and four 20-byte inputs; 2,943 `dragTarget` cases — every slot list of length 0..3 over a five-rectangle alphabet (same-size neighbours, a large slot next to a small one, a same-center pair in both orders, a nested triple), every `draggedIndex` in `0..length`, a 27-point pointer lattice over interiors, edges, gaps and outside, every `previous.banned` in `none | 0..length-1`, and `previous.target = draggedIndex` plus one shifted target where there is more than one slot). `ResearchFormal/Basic.lean` holds only two shared rewriting helpers for `if`, no app theorems.
2. `tests/formal/conformance.test.ts` replays every vector against the TypeScript implementation in the normal test run. It needs no Lean toolchain.
3. `bun run formal:check` (CI job `formal`) rebuilds the proofs, rejects `sorry`/`axiom`, regenerates the vectors and fails if they differ from the committed file.

So a change to the TypeScript that departs from the model fails step 2, and a change to the model that is not re-exported fails step 3.

## What is not proved

- The correspondence is tested on finite grids, not proved for all inputs. The grids are exhaustive over the discrete structure (every state, every branch of every condition) but not over unbounded numbers or arbitrary strings.
- Floating-point behaviour (NaN handling in budgets, CAGR, PER, margins) is covered by unit and property tests, not Lean: the models use natural numbers.
- Time is abstracted to one bit (`leaseExpired`); clock skew is outside the model. Fencing does not depend on clocks, which is the point of the generation counter.
- The reducer model abstracts component props and reference checks (datasets, sources); those are covered by unit, property and integration tests.
- SQL-level atomicity (the guarded D1 batches) is exercised by integration tests in the Workers runtime, not modelled.
- Feed parsing, URL/IP classification and claim text matching are not modelled.
- String truncation (`truncateText`, now in `packages/domain/src/text/truncate.ts`) and the context builder's text handling in `buildConversationContext` (trimming, the per-message cut, UTF-8 byte counting) are covered by unit and property tests, not by Lean; only the selection count (`recentCountWithinBudget`) is modelled.
- The dashboard model abstracts widget props and the 30-series limit (titles, sizes, series sets); those are covered by unit, property and contract tests. `replace` (same widget id) is structurally the identity and `reset` installs a schema-validated dashboard, so neither needs its own operation in the model.
- The rate-window model counts whole time units; sub-millisecond timing and the runner's sleep/pacing are outside the model. The bound assumes grants are recorded in clock order, which holds because the runner appends them as they occur.
- The calendar fold model abstracts characters to their UTF-8 widths (1..4 octets): the implementation never looks at the characters themselves, only at each one's width, and the conformance test replays every vector through real one- to four-octet characters. The selection model abstracts validated ISO dates to day offsets from a fixed base (lexicographic string order is chronological order on validated `YYYY-MM-DD`); invalid date strings, negative or fractional counts and undecided dates are outside the Nat model and are covered by unit tests plus a fail-closed conformance section.
- The month-grid model proves the combinatorial core (offsets in `Nat`); the absolute civil-date correspondence (leap years, the 1970 Thursday anchor, Hinnant arithmetic) is an independent Lean reimplementation used only for the 27 exported vectors, tied to the TypeScript by the conformance test and by hand-worked unit tests — tested on samples, not proved. `shiftMonth` and `groupEventsByDate` are covered by unit tests, not modelled.
- The sync-plan model abstracts all compared fields to one fingerprint per event (equal iff every compared field is equal) and ids to small `Nat`s; duplicate ids in either input are outside the model (the implementation fails closed with `DUPLICATE_ID`) and are covered by unit tests plus a fail-closed conformance section. The exact ascending output order is pinned by the vectors and asserted in the conformance test; only membership is proved about the model's sorts. The base32hex encoder has vectors plus a proved output-length property; the digest canonical form (`canonicalGoogleSyncDigestInput`) is covered by unit tests and the bench case, not modelled.
 - The drop-target model uses integers for coordinates while the implementation uses doubles; every conformance vector is integral so the two agree exactly, and the doubled-center dot product has the same sign as the midpoint version. Slot measurement from the DOM, the `requestAnimationFrame` coalescing and the page-coordinate conversion in the drag engine are outside the model and covered by E2E; a negative `draggedIndex` is outside the `Nat` model (the implementation holds still for it, as for any out-of-range index). `banned_only_while_inside` assumes the engine invariant `previous.target = draggedIndex`, which is what the engine passes; histories with a different target are covered by vectors but not by that theorem.

## Running

```sh
# one-time: install the Lean toolchain manager (https://lean-lang.org/install/)
bun run formal:check          # lake build + no-sorry check + vectors are current
bun run test                  # includes tests/formal/conformance.test.ts
```
