# Materials database and widgets

Implemented scope: migration `0016_material_series.sql` stores owner-imported physical-material snapshots and observations. Home and Notebook chart, indicator and metric widgets read them from SQLite/D1 through the same bounded market-data API as FRED/Twelve Data. No stock or ETF substitution occurs. The full [metals database design](METALS_DATABASE_DESIGN.md) remains a roadmap; normalized material/product registries, provider downloads, automatic revision selection, composites and FX conversion are not implemented.

## Import and display

POST `/api/v1/materials/imports` with the version-1 payload illustrated by [the synthetic fixture](../examples/materials/fixture.ts). Authenticate as owner and supply the normal CSRF header (`X-Research-Csrf: 1`) and same-origin `Origin`. The fixture is documentation/test data only and is never automatically imported. Use authorized real observations for your own charts.

Each series has a unique `materials:<ID>` (1–25 uppercase ASCII letters/digits), material, product, grade, assessment basis, source ID, publisher, HTTPS source link, unit, frequency, retrieval instant and observations. Define unit and basis precisely (currency, mass/content denominator, delivery market, tax basis). Different sources/grades/bases use different IDs. Each observation supplies an assessment date, exact canonical decimal and nullable `materialsSourceUpdatedAt`. Date-only source updates must not be invented as exact timestamps.

After import, open Add widget → Line chart / Indicator table / Market metric and select the imported series from Commodities. Home and Notebook share the database-backed selector. The widget's Material details disclose product, grade, assessment basis, source identity, exact original values and per-observation source update times; plotted values are floating-point display projections. Material prices are stored independently of the widget arrangement and survive removing a widget and restarting the app.

GET `/api/v1/materials/series/:seriesId` returns the exact source snapshot. Existing owner authentication, CSRF protection and safe error responses apply. Import replays with the same normalized content are idempotent (observation order is ignored). Changed snapshots return 409 without writing any part of the batch. Corrections or additional dates currently require a new series-version ID and an explicit widget selection; historical widget definitions never silently switch sources or versions. Unknown IDs show no data and no fabricated provider URL.

## Bounds and storage

- At most 20 series per request; 800 distinct assessment dates per series; 750,000 request bytes; 200 stored series per owner. The last bound includes historical versions. Imports at the limit return 409; no catalog results are silently truncated.
- Titles: 120 characters, unit: 80, material/product/grade/basis/publisher: 200, source ID: 64. Contracts reject oversized values before persistence. Source URLs use the project's bounded HTTPS URL validator.
- Exact amounts follow `equityDecimalSchema`: canonical decimal text, up to 100 significant digits and 30 fractional digits, with a 132-character ceiling. No exponent notation, padded zeroes or nonfinite chart projections. Charts may round for display; Material details retains original decimal text.
- `materials_source_updated_at` is nullable SQLite TEXT, exactly 24 characters in UTC with milliseconds, e.g. `2026-10-29T09:30:45.000Z`. The API validates real calendar dates; SQL enforces type, length and canonical calendar round trip. The source update cannot follow retrieval, and an assessment cannot be dated after retrieval. Retrieval cannot be in the future. Unknown timestamps remain NULL.
- `metal_series` stores immutable source snapshots with normalized metadata columns for catalog/ETag reads; `metal_observation` stores exact prices and timestamps keyed by owner/series/date. Primary keys cover the widget read paths, with no extra price indexes. Both inserts form one guarded atomic batch. Decimal/calendar validation is authoritative at the typed API boundary; direct SQL writes are not a supported import interface.

Imported materials are never sent to FRED or Twelve Data by the runner. Refresh only fetches external series. Material rows are not cleared by market-cache pruning. There is no automatic feed subscription, material import UI, deletion/archival workflow or Notebook assistant discovery of the imported catalog yet; manual widget selection works. Obtain source access/rights before importing licensed data. The importer records user-supplied provenance rather than verifying provider claims or license entitlements.

## Validation

API tests cover real Node SQLite and Workers D1: imports/replay/conflicts, atomic rollback, source isolation, invalid timestamps/dates/titles, Home/Notebook parity, widget removal and exact provenance. A browser spec exercises chart and indicator display, source links, details, catalog selection and reload. A real-environment spec starts `bun run dev` from a pristine working-tree copy with throwaway data/ports and confirms persistence after restarting the actual launcher. Its input is explicitly synthetic owner-import data; it proves the import/read/display path, not a live metals-provider feed or an agent research turn.

Claude Code reviewed the change. Review fixes include bounded titles/catalog size, metadata projections, observation-order canonicalization, missing-series behavior, provenance disclosure, future-date rejection, JSON 413 responses, explicit UNION columns and immutable row keys. SQLite/D1's short GLOB-pattern limit required removing the long timestamp GLOB from the unshipped migration 0015 as well as 0016; fixed-length canonical `strftime` round-trip validation supplies the format check without that runtime failure. No operational database was changed by these tests.
